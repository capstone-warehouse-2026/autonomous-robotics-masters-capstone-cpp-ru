# Два физических робота Webots

`warehouse.wbt` использует ту же статическую геометрию и карту, что однороботный
стенд `simulation/integration`. `robot_1` стартует в `(-3,-3,0)`, `robot_2` —
в `(3,-3,π)`. Их встречные маршруты проходят южнее центрального стеллажа;
ряд `y=-4` оставляет пространство для разрешения конфликта.

Модель находится в локальном `protos/FleetRobot.proto`, сетевые ассеты не нужны.
Радиус корпуса — 0.28 м, колёса — 0.0985 м, колея — 0.4044 м. Вращение колёс,
контакты, энкодеры и LiDAR вычисляет физический движок Webots.

Корпус этой версии выше однороботного: он пересекает плоскость сканирования,
поэтому роботы видят друг друга настоящим LiDAR. `near=0.30` отсекает собственный
корпус радиуса 0.28; это геометрическая настройка камеры глубины, без фильтрации
по истинной позиции другого робота. `minRange=0.31`, дальность — 12 м.

Для каждого робота запускается отдельный внешний `webots_bridge`:

```bash
"$WEBOTS_HOME/webots-controller" --port=12591 --robot-name=robot_1 \
  ros2_ws/install/capstone_webots_bridge/lib/capstone_webots_bridge/webots_bridge \
  --ros-args -r __ns:=/robot_1 -r /tf:=tf -r /tf_static:=tf_static \
  -r clock:=/clock -p absolute_time:=true -p enable_reset:=false -p publish_clock:=true
```

Для `robot_2` меняются имя/namespace и `publish_clock:=false`. Только первый
bridge публикует `/clock`; обе модели имеют `synchronization TRUE` и используют
единое абсолютное время физического мира. Индивидуальный reset отключён:
новый опыт запускается в новом экземпляре Webots, без скачка времени одного
робота относительно другого.

Nav2 для первого робота:

```bash
ros2 launch capstone_nav2 fleet_robot.launch.py namespace:=robot_1 \
  map:="$PWD/simulation/fleet/map.yaml" initial_x:=-3 initial_y:=-3 initial_yaw:=0
```

У второго — `namespace:=robot_2`, `initial_x:=3`, `initial_yaw:=3.141592653589793`.
TF-топики разделены (`/robot_1/tf`, `/robot_2/tf`), при этом frame_id остаются
`map`, `odom`, `base_link`. Координаты обеих карт соответствуют одному складу.
Истинная поза публикуется только в `/robot_N/evaluation/ground_truth` для проверки.

Запущены AMCL, map_server, Nav2 planner/controller и существующий safety monitor.
Fleet executor направляет согласованные CBS/ECBS отрезки в
`/robot_N/control/follow_path`; RPP исполняет каждый отрезок, а общий барьер
разрешает следующий только после подтверждённой остановки всех роботов.
Локальный `SimpleGoalChecker` проверяет геометрию цели с допуском 0.03 м / 0.10 рад.
RPP использует lookahead 0.4 м и сначала разворачивается к пути до ошибки менее
0.15 рад. Это уменьшает боковое отклонение после смены направления на коротком
ребре. Физический аудитор сохраняет независимый допуск коридора 0.12 м;
допуск Nav2 меньше, чтобы оставить запас на погрешность локализации и остановку.
После его успеха Nav2 публикует нулевую команду. Fleet barrier независимо ждёт
свежую неподвижную odom в течение 0.2 с симуляционного и монотонного времени;
только затем начинается следующий шаг. Проверка остановки вынесена из Nav2 goal
checker: небольшие угловые коррекции RPP не должны мешать завершению геометрической
цели, а движение после result всё равно блокирует общий барьер.

Точки пути задают неподвижные цели в `map`, поэтому их `PoseStamped.header.stamp`
равен нулю: TF преобразует цель по актуальной связи `map → odom`. Время создания
пути сохраняется в `Path.header.stamp`. Это существенно для Jazzy: RPP преобразует
путь на текущее время, а goal checker сохраняет stamp конечной точки. Если присвоить
ей время отправки, после коррекции AMCL контроллер и goal checker могут проверять
разные положения цели; робот тогда вращается на месте до ошибки отсутствия
прогресса. Stamp измерений AMCL, odom и scan при этом сохраняются без изменений.
Полный сценарий и оценка конфликтов принадлежат пакетам флота.
