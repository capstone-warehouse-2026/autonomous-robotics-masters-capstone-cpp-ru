# CBS, ECBS и назначение заявок флоту

`capstone_fleet` — C++17 библиотека без ROS-зависимостей. ROS-исполнение,
жизненный цикл заявок, Nav2 и физическая проверка находятся в пакете исполнения
флота. Этот пакет рассчитывает назначение и совместный дискретный маршрут.

## Алгоритмы

CBS использует дерево ограничений на верхнем уровне и оптимальный поиск
одного робота в пространстве `(клетка, время)` на нижнем. Найденный конфликт
создаёт две ветви: в каждой запрещается соответствующее действие одного
участника. Раскрывается узел с минимальной суммой стоимостей путей.
Основа: [Sharon et al., CBS, 2015](https://tzin.bgu.ac.il/~felner/2015/CBSjur.pdf).

ECBS реализует FOCAL на **обоих** уровнях. Нижний уровень выбирает внутри
`f ≤ w·min(OPEN.f)` по числу конфликтов и возвращает путь вместе с `f_min`.
Для узла дерева `LB = Σ f_min`; верхний FOCAL включает узлы с
`cost ≤ w·min(OPEN.LB)`, предпочитая меньше конфликтов. Коэффициент `w`
не перемножается сам на себя. Основа:
[Barer et al., Enhanced CBS, 2014](https://cdn.aaai.org/ojs/18315/18315-77-21831-1-2-20210717.pdf).

Начальные независимые A* маршруты одинаково рассчитываются для обоих методов
и сохраняются в результате. Это показывает исходные конфликты до совместного
поиска. Счётчики `*_focal_slack_expansions` показывают, использовал ли ECBS
разрешённый выбор узлов сверх текущей минимальной оценки.

## Модель движения и стоимость

`Grid` содержит четыре соседних направления и ожидание. `origin_x/y` — мировой
центр клетки `(0,0)`, а `resolution` — расстояние между центрами. Занятые клетки
и `blocked_edges` задаёт вызывающий код по карте и геометрии робота; запрещённое
ребро непроходимо в обе стороны. `shortest_distance` учитывает оба ограничения.

Проверяется занятость вершин и расстояние между **полными отрезками** переходов
двух роботов за один раунд. При расстоянии меньше `clearance` возникает конфликт.
Так обнаруживаются обмен клетками, пересечение, движение следом через одну
клетку, а также движение мимо ожидающего робота. Это консервативная модель:
два пересекающихся перехода не разрешаются даже при возможности разнести
прохождение точки внутри раунда по времени.

Исполнитель обязан дождаться прибытия и остановки всех участников раунда,
прежде чем начинать следующий. Для переноса этого условия на физику нужно
контролировать отклонение от отрезка и запас `clearance` относительно радиусов
и погрешности слежения. Оптимальность CBS и граница ECBS относятся к этой
дискретной модели, а не к времени доставки с разворотами, ускорением и Nav2.

Стоимость — сумма числа действий до **последнего прибытия** на цели. После
прибытия цель занята постоянно. Поиск учитывает ограничения после раннего
прибытия и может временно освободить цель для другого робота. Возвращённые пути
дополнены ожиданиями до общей длины; эти дополнительные ожидания не увеличивают
стоимость результата.

## API и ограничения

Основной интерфейс — `include/capstone_fleet/planner.hpp`:

```cpp
capstone_fleet::PlanOptions options;
options.method = capstone_fleet::Method::ECBS;
options.weight = 1.5;
options.clearance = 0.85;
const auto result = capstone_fleet::plan(grid, starts, goals, options);
```

`Success` означает наличие проверенного совместного плана. `NoSolution`
означает исчерпание вариантов **в заданном `max_time_steps`**, а не доказательство
невозможности при неограниченном времени. `ResourceLimit` отдельно сообщает
превышение времени/числа раскрытий; такую ветвь нельзя молча отбросить и
продолжать заявлять оптимальность. `InvalidInput` указывает неверную карту,
параметры или пересекающиеся начальные позиции.

Для успешного CBS `cost` оптимален в ограниченной модели, для ECBS:
`lower_bound ≤ optimal_cost ≤ cost ≤ w·lower_bound ≤ w·optimal_cost`.
Проверяются положительные размеры карты, конечные координаты, свободные
начала/цели, границы горизонта и ресурсов.

`minimum_cost_assignment(costs)` принимает матрицу `robots × jobs`, где
отрицательная стоимость запрещает назначение. Последовательные кратчайшие
увеличивающие пути в остаточной сети сначала максимизируют число назначений,
затем минимизируют суммарную стоимость. Обратные рёбра позволяют исправлять
раннее локально выгодное назначение. Ни робот, ни заявка не появляются в
результате дважды. Отбор выпущенных заявок по срокам и сохранение владельца
у выполняемых заявок остаются обязанностью диспетчера.

## Проверки

`test_fleet_planner` проверяет:

- оптимальность CBS относительно независимого Dijkstra на всех 900 парах
  двухроботных начал/целей сетки 3×2;
- границу ECBS при `w=1.1, 1.5, 2.0` относительно того же оптимума, включая
  отдельную проверку реального использования FOCAL;
- встречный обмен местами с объездом, сохранение занятости цели, временный уход с цели;
- геометрические конфликты вершин/рёбер и явный отказ при недостаточном горизонте;
- ограничения ресурсов, некорректные входы и непроходимые статические рёбра;
- назначение против полного перебора 50 матриц, запрет повторных назначений.

Эти тесты подтверждают библиотеку планирования. Физические доставки должны
дополнительно проходить в Webots с Nav2 и независимой проверкой траекторий.
