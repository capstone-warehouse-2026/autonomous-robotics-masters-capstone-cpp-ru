# Исполнение совместного плана CBS/ECBS через Nav2

`fleet_coordinator` распределяет заявки между роботами и исполняет совместные
маршруты библиотеки `capstone_fleet`. Локализация, контроллер, costmap и safety
monitor работают отдельно для каждого робота. Координатор не подписывается
на ground truth Webots.

## Распределение и выполнение

Записи заявок `capstone_mission::Job` и их валидация переиспользованы из G5.
Отдельная `FleetJobQueue` хранит владельца каждой заявки и проверяет ограничение
вместимости отдельно для каждого робота. Очередь одиночного G5 сохраняет своё
прежнее ограничение одной активной доставки на систему.
Из уже поступивших заявок выбирается EDF-пакет размером не больше числа свободных
роботов. Минимальное по сумме назначение использует кратчайшее число шагов от
робота до pickup на статической карте. Заявка закрепляется за одним роботом до
доставки; вместимость каждого робота — один груз. Это явный базовый диспетчер
флота; обученный DQN одиночного G5 здесь не выдаётся за многороботную политику.

Статическая карта приходит через `/<первый робот>/map`. Решётка задаётся в YAML;
её клетки и рёбра проверяются по OccupancyGrid с радиусом 0.4 м. Неизвестные
клетки считаются занятыми. CBS/ECBS получает одновременно начальные и целевые
клетки всех роботов, включая ожидание свободного робота на его текущей клетке.

Состояния координатора: ожидание готовности → назначение → асинхронное
планирование → исполнение раундов → обслуживание у станции → следующая стадия.
Планирование имеет deadline 5 секунд и не блокирует ROS callbacks.

Каждый раунд разрешает роботу пройти одно соседнее ребро либо остаться на месте.
Ребро отправляется как прямой `nav_msgs/Path` в его Nav2 `FollowPath`. Следующий
раунд начинается только после `SUCCEEDED`, свежей одометрии с нулевой скоростью
не менее 0.2 с по stamp и steady-времени получения и локализации в пределах 0.12 м
от целевой клетки у **всех** роботов. Каждый одометрический образец проверяется:
краткое движение между двумя вызовами таймера сбрасывает интервал тишины.
Ожидание результата action и состояние заявки ведутся отдельно.

Проверка конфликта в планировщике использует расстояние между целыми отрезками
движения внутри раунда, минимум 0.85 м. Поэтому безопасность плана не зависит
от совпадения мгновенных скоростей двух роботов. Физический корпус имеет радиус
0.28 м, Nav2 допускает ошибку достижения 0.03 м; независимый evaluator проверяет
фактические траектории и контакты в Webots.
Во время исполнения координатор также контролирует отклонение локализованного
робота от зарезервированного ребра или точки ожидания. Выход более чем на 0.12 м
вызывает отмену движения всего флота с причиной `left_reserved_corridor`.

Время загрузки и разгрузки моделируется стоянкой на станции из YAML. Физическая
манипуляция грузом не моделируется. При недостижимом совместном плане, устаревших
входах или ошибке action координатор отменяет принадлежащие ему цели и требует
подтверждения результата и остановки. Неизвестный результат отмены либо остановка
без подтверждения завершаются ошибкой. Повторного назначения потерянного груза нет.

Обратный скачок часов считается ошибкой активного эпизода флота. Каждый физический
прогон запускается из нового мира Webots. Краткое опережение `/clock` сообщениями
odom/pose буферизуется с сохранением исходного stamp и steady-времени поступления;
порог свежести остаётся 300 мс.

## Интерфейс

```bash
ros2 run capstone_fleet_runtime fleet_coordinator --ros-args \
  -p use_sim_time:=true \
  -p manifest_path:=/absolute/path/to/scenarios/swap.yaml \
  -p output_directory:=/tmp/fleet-new-run \
  -p method:=cbs
```

Для ECBS: `-p method:=ecbs -p weight:=1.5`. Перед запуском должны быть активны
Webots bridge, AMCL/Nav2 и safety monitor каждого робота. Подробный общий запуск
содержится в корневом README проекта.

`scenarios/swap.yaml` содержит две встречные доставки. В `scenarios/queued.yaml`
ещё две заявки поступают на пятой секунде, пока роботы заняты первой парой.
После доставки они назначаются освободившимся роботам с учётом новых положений;
один и тот же робот не может владеть двумя активными грузами одновременно.

Входы для каждого `robot_id`: `/<id>/localization/pose`, `/<id>/state/odom`,
`/<id>/control/follow_path`. У всех локализаций общая система координат карты,
а деревья TF изолированы по namespace. Сервис `fleet/cancel` начинает асинхронную
отмену. `fleet/status` публикует `capstone_fleet/mission` со состоянием эпизода.
Завершение процесса с кодом 0 означает доставку всех заявок с подтверждённой
остановкой; отмена и любой отказ возвращают ненулевой код.

## Доказательства

- `events.csv`: абсолютное ROS-время, назначение, pickup/delivery и границы раундов.
- `assignment_N.yaml`: EDF-пакет, матрица расстояний, выбранные пары и сумма.
- `plans.csv`: независимые и разрешённые пути в мировых координатах.
- `plans/plan_N.yaml`: CBS/ECBS, стоимость в шагах решётки, lower bound, коэффициент
  допустимой субоптимальности, конфликты и число расширений поиска.
- `fleet_episode.yaml`: терминальная причина и состояния всех заявок.

Один лишь успешный action не является свидетельством физической доставки:
проверка ground truth выполняется отдельным evaluator родительского стенда.
