# Проверенные физические испытания флота

Артефакты испытаний двух роботов в Webots R2025a с Nav2 1.3.14, ROS 2 Jazzy
и общей очередью из четырёх заявок. Назначение: ближайший срок в партии,
затем минимальная суммарная длина пути до пунктов погрузки; вместимость робота —
одна заявка. Совместные маршруты рассчитывает CBS/ECBS, исполняет Nav2.

## Подтверждённые прогоны доставки

[CBS-аудит](cbs-queued/physical/audit.yaml) и
[ECBS-аудит](ecbs-queued/physical/audit.yaml) содержат
`success: true`, `terminal: completed`. Исходные запуски —
`results/fleet-cbs-qualified` и `results/fleet-ecbs-qualified`,
25 ноября 2026 года. Для ECBS использован коэффициент `w=1.5`.

| Показатель | CBS | ECBS, w=1.5 |
|---|---:|---:|
| Доставлено | 4 из 4 | 4 из 4 |
| Время миссии по часам симуляции | 121.24 с | 121.20 с |
| Завершённые совместные раунды | 16 | 16 |
| Назначения партий / совместные планы | 2 / 4 | 2 / 4 |
| Физические контакты robot_1 / robot_2 | 0 / 0 | 0 / 0 |
| Минимальное измеренное расстояние между центрами | 0.960612 м | 0.943598 м |
| Путь robot_1 / robot_2 по ground truth | 15.679083 / 11.851010 м | 15.653689 / 11.858288 м |
| Максимальное отклонение от исполняемого отрезка | 0.097055 м | 0.096833 м |
| Максимальная ошибка позиции обслуживания | 0.073284 м | 0.067375 м |
| Максимальный интервал физических отсчётов | 0.020000 с | 0.020000 с |
| Синхронные парные отсчёты | 6388 | 6347 |

Подтверждены погрузка и доставка каждого груза у соответствующей станции,
по 1 с неподвижного обслуживания, отсутствие контактов и остановка обоих
роботов после завершения. Это измерения данного прогона; дискретные отсчёты
не являются самостоятельным доказательством безопасности между отсчётами.

[График CBS](cbs-queued/trajectory.png) и
[график ECBS](ecbs-queued/trajectory.png) сравнивают независимые A*, совместный
план и реальное движение для плана №2. Нижняя панель показывает расстояние
между роботами на протяжении всей миссии. Файлы построены из сохранённых CSV;
минимум расстояния дополнительно сверен с соответствующим физическим аудитом.

В [первой партии](cbs-queued/runtime/assignment_1.yaml) матрица стоимости
`[[0, 6], [6, 0]]`, во [второй](cbs-queued/runtime/assignment_2.yaml) —
`[[6, 0], [0, 6]]`. В обоих случаях выбраны два различных робота и две
различные заявки с общей стоимостью 0. Пункты погрузки второй партии расположены
у текущих позиций роботов: стоимость альтернативной погрузки составляет
шесть свободных рёбер сетки. В ECBS-прогоне записаны те же матрицы и назначения.

Стоимость пересчитана непосредственно из `runtime/plans.csv`: сумма действий
до последнего прибытия на цель, без добавленных конечных ожиданий.

| План | Независимые пути | CBS / ECBS | LB CBS / ECBS | Конфликты до → после |
|---|---:|---:|---:|---:|
| 1, погрузка | 0 | 0 / 0 | 0 / 0 | 0 → 0 |
| 2, доставка | 12 | 14 / 14 | 14 / 13 | 2 → 0 |
| 3, следующая погрузка | 0 | 0 / 0 | 0 / 0 | 0 → 0 |
| 4, обратная доставка | 12 | 14 / 14 | 14 / 13 | 2 → 0 |

Для встречного обмена целями необходимо 12 горизонтальных действий.
Чтобы поменять порядок роботов без пересечения, хотя бы один должен покинуть
исходную строку сетки и вернуться на неё: ещё минимум два вертикальных
действия. Записанная стоимость 14 достигает этой нижней границы.
Гарантия относится к дискретным раундам, а не к физическому времени с
разворотами и разгоном. Результаты сверки сохранены в
[CBS independent_checks.yaml](cbs-queued/independent_checks.yaml) и
[ECBS independent_checks.yaml](ecbs-queued/independent_checks.yaml).

Для каждого из двух планов обмена ECBS удовлетворяет границе
`cost=14 ≤ w·LB=1.5·13=19.5`. В данном сценарии он также нашёл оптимальную
стоимость 14. CBS раскрыл 4 узла верхнего и 84 нижнего уровня; ECBS — 2 и 42.
У ECBS счётчики выбора узлов сверх минимального `f` равны 1 на верхнем и 16
на нижнем уровне, то есть FOCAL действительно использовал разрешённое
ослабление. Такие результаты одного сценария не доказывают преимущество
во времени физических доставок или масштабируемость на большой флот.

## Отмена во время движения

[cancel/physical/audit.yaml](cancel/physical/audit.yaml) подтверждает
`success: true`, `terminal: cancelled` для ECBS в сценарии `fleet_swap`
с двумя заявками. Оба робота загрузили свои грузы; доставок нет, поскольку
оператор отменил миссию во время выполнения второго раунда движения.
Исходный запуск — `results/fleet-cancel-qualified`.

| Показатель | Результат |
|---|---:|
| Доставлено | 0 из 2, отмена |
| Время до конечного статуса от начала миссии | 8.88 с |
| Завершённые / прерванные раунды | 1 / 1 |
| Путь robot_1 / robot_2 по ground truth | 1.527150 / 1.487009 м |
| Минимальное расстояние между центрами | 2.987944 м |
| Максимальное отклонение от отрезка | 0.052854 м |
| Контакты robot_1 / robot_2 | 0 / 0 |

В журнале `stopping: operator_cancel` записано при `sim_time=20.16`,
`fleet_stopped` — при `20.44`: задержка до подтверждения остановки самим
исполнителем составляет 0.28 с. Это не время завершения независимого аудита:
он дополнительно требует не менее 0.3 с физической неподвижности после
конечного статуса, свежую одометрию и измерения контактов обоих роботов.
[График отмены](cancel/trajectory.png) показывает исполненную часть маршрутов
и фактические точки остановки; полные согласованные планы показаны отдельно.
Прерванный второй раунд не засчитан как завершённый.

## Состав и воспроизведение

Каждая папка прогона содержит исходные `runtime/`, `physical/`, `scenario.yaml`,
`provenance.json`, журналы процессов без служебного `logs/ros/`, график
и `artifacts.sha256`. Provenance сохранён без изменений: он фиксирует хеши
исходников на момент запуска. После фиксации provenance CBS исправлено только описание
допуска достижения цели в `ros2_ws/src/capstone_fleet_runtime/README.md`
с 0.06 на 0.03 м;
на момент сохранения остальные 65 хешей совпали. Для ECBS и отмены совпали
все 66 записанных хешей. Исполняемые исходники и launch-файлы не изменялись
относительно provenance; дальнейшие изменения документации не исправляют
задним числом исходный provenance.

Проверенные исходники впоследствии зафиксированы локальным коммитом `841f888`.
Оригинальный provenance сохраняет состояние на момент запуска:
`code_commit=7821de94c14ccc3e6cae194d8676f5edca8a4f3c`, `worktree_dirty=true`
и отдельные SHA256 файлов; поле commit намеренно не переписано новым хешем.

Из корня репозитория график можно пересоздать так:

```bash
python3 scripts/plot_fleet_results.py \
  --run experiments/fleet/cbs-queued \
  --map simulation/fleet/map.yaml \
  --output /tmp/fleet-cbs-trajectory.png
```

Проверка целостности из папки соответствующего прогона:

```bash
sha256sum -c artifacts.sha256
```

Команда физического запуска целиком записана в `provenance.json`; подготовка
стенда описана в [docs/FLEET_CBS_ECBS.md](../../docs/FLEET_CBS_ECBS.md).

## Проверки программных компонентов

В [validation/](validation/) сохранены журналы выполненных проверок:

- `fleet-final-test-results.log`: 180 записей colcon, без ошибок, провалов
  и пропущенных проверок; это итог агрегатора, не число физических сценариев.
- `fleet-runtime-final-test.log`: 21 gtest пакета исполнения; colcon учитывает
  также запись запуска всего набора, поэтому его итог для пакета — 22.
- `fleet-evidence-final-tests.log`: 37 Python-тестов независимых аудиторов.
- `fleet-evidence-capture-lint.log`: свежая единая проверка десяти Python-файлов,
  включая observer, оба построителя графиков и launch-файлы; замечаний нет.

Сохранены также исходные журналы двух предыдущих проверок Python-стиля.
`validation/artifacts.sha256` защищает целостность этих отчётов. Проверки C++
при сохранении артефактов повторно не запускались.
