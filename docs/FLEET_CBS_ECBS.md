# Распределение заявок и CBS/ECBS в Webots

Ветка `integration/g5-nav2-webots` содержит двухроботный физический стенд.
Каждый робот получает заявки, оценивает положение через AMCL, исполняет путь
контроллером Nav2 и передаёт команды через отдельный safety monitor.
Центральный координатор рассчитывает назначения и совместные маршруты.

## Как запустить

Нужны Ubuntu 24.04 x86_64, ROS 2 Jazzy и Nav2. Docker для этих команд не нужен.
Установка Webots локальная, в `.cache/`; официальный архив проверяется по SHA256.

```bash
# Если Nav2 ещё не установлен:
sudo apt install ros-jazzy-navigation2 ros-jazzy-nav2-bringup xauth

# Из корня репозитория:
make fleet-setup
make fleet-build
make fleet-test FLEET_METHOD=cbs
make fleet-test FLEET_METHOD=ecbs
```

Для окна симулятора добавьте `FLEET_ARGS='--gui'`. Для своего каталога результатов:

```bash
make fleet-test FLEET_METHOD=ecbs \
  FLEET_ARGS='--weight 1.5 --output results/ecbs-demo'
```

Для четырёх заявок, включая две поступающие во время движения:

```bash
make fleet-test FLEET_METHOD=cbs \
  FLEET_ARGS='--manifest ros2_ws/src/capstone_fleet_runtime/scenarios/queued.yaml'
make fleet-test FLEET_METHOD=ecbs \
  FLEET_ARGS='--manifest ros2_ws/src/capstone_fleet_runtime/scenarios/queued.yaml --weight 1.5'
```

Каталог должен быть новым. По умолчанию используется отдельный `ROS_DOMAIN_ID=193`;
для параллельного прогона задайте другой `--domain`. Скрипт ждёт активации всех
Nav2-компонентов, запускает независимый сбор физических измерений, затем миссию.
После завершения он ждёт физической остановки и результата проверки.
При ошибке возвращает ненулевой код и сохраняет логи.

Перед запуском координатора оценщик требует секунду непрерывно свежих физических
потоков. Во время запуска связи возможна пауза неподвижного симулятора; строгий
контроль пауз получения контактов включается при статусе `running` или первом
наблюдаемом движении, включая вращение, и далее не выключается. Причина и время
включения сохраняются в `monitoring_armed`. Контакты, геометрия и скачки позиции
проверяются с первого измерения; контроль пропусков симуляционных измерений
включается после готовности подписок.

## Что именно происходит

В сценарии `swap.yaml` два робота стоят в `(-3,-3)` и `(3,-3)`. Каждый должен
забрать груз у своей стартовой станции и доставить на противоположную.
Их независимые кратчайшие маршруты идут навстречу друг другу. Совместный
планировщик должен обнаружить эти конфликты и использовать ожидание или объезд
по соседнему проходу. Просто выполнить два непересекающихся маршрута для
успешной проверки недостаточно: аудитор требует исходный конфликт.

В `queued.yaml` первые две доставки такие же. Ещё две заявки поступают через
5 секунд после старта миссии, когда оба робота уже заняты. Они остаются в очереди
до завершения первого рейса; новое назначение учитывает изменившиеся положения
роботов. Это проверяет повторное распределение, а не только разовую выдачу целей.

Назначение выполняется при освобождении роботов. Сначала выбираются поступившие
заявки с наиболее ранними сроками; затем `min-cost max-flow` сопоставляет выбранные
заявки свободным роботам по кратчайшему расстоянию до места загрузки. Один робот
несёт одну заявку, у заявки один владелец. `FleetJobQueue` использует типы заявок
из `capstone_mission` и хранит владельца каждой заявки: назначение → загрузка →
доставка. Ограничение одиночной очереди G5 сохранено отдельно. Погрузка и разгрузка
моделируются временем обслуживания на станции.

Роботы движутся физически: команды вращают моторы, одометрия рассчитывается
по энкодерам, LiDAR формируется рендерингом Webots. Истинные позиции читаются
только независимым оценщиком. Координатор использует локализацию AMCL и карту.
LiDAR видит корпус другого робота; локальный costmap и safety учитывают его
как препятствие.

## CBS и ECBS

CBS строит дерево ограничений. Для каждого робота нижний поиск A* находит маршрут
в пространстве «клетка, шаг». При обнаружении конфликта верхний уровень создаёт
две ветви, запрещая конфликтующий переход поочерёдно каждому участнику.
Выбирается узел с минимальной суммарной стоимостью путей.

ECBS использует FOCAL на обоих уровнях. Внутри допустимой границы `w` он предпочитает
варианты с меньшим числом конфликтов. Возвращается также нижняя оценка стоимости;
верхняя граница относится к сумме действий в дискретной модели. Подробности,
первоисточники и API находятся в [README планировщика](../ros2_ws/src/capstone_fleet/README.md).

Карта разбивается на клетки с шагом 1 м. Занятость клеток и переходов рассчитывается
по настоящему `OccupancyGrid` с учётом радиуса планирования 0,4 м. Возможны четыре
направления и ожидание. После прибытия робот продолжает занимать цель.

Конфликт проверяется между полными отрезками перемещений в одном раунде: расстояние
должно быть не меньше 0,85 м. Поэтому пересечение, встречный обмен клетками и
движение следом через только что освобождаемую клетку требуют разведения по
раундам. Это консервативнее модели точечных роботов с одинаковой скоростью.

Исполнитель посылает каждому роботу прямой участок через `FollowPath` и ждёт
окончательного результата action, прибытия и устойчивой остановки всех участников.
Затем открывает следующий раунд. Развороты и неодинаковое время движения не
требуют от роботов попасть в жёсткий секундный интервал. Стоимость CBS/ECBS
считается в шагах; это не обещание оптимального физического времени доставки.

В профиле флота `SimpleGoalChecker` завершает action по геометрическому допуску
0,03 м и 0,10 рад; Nav2 публикует нулевую команду. После этого координатор отдельно
требует свежую одометрию с устойчивой остановкой не менее 0,2 с по времени
симуляции и монотонному времени получения. Завершение action не открывает
следующий раунд само по себе.

RPP сначала выравнивает направление до ошибки менее 0,15 рад. Более широкий
порог исходного профиля позволял начинать поступательное движение во время
разворота и давал лишнее боковое отклонение на коротком метровом участке.

Точки пути заданы в статической карте и используют stamp `0` для выбора текущего
TF `map→odom`. Метка заголовка самого пути сохраняет время отправки. Иначе
goal checker Nav2 Jazzy проверяет конечную точку через старое преобразование,
а RPP использует новую поправку AMCL: цель может перестать сходиться.
Метки измерений LiDAR, odom и AMCL при этом не изменяются.

## Основные места в проекте

| Путь | Назначение |
|---|---|
| `ros2_ws/src/capstone_fleet` | CBS, ECBS, геометрические конфликты, назначение заявок |
| `ros2_ws/src/capstone_fleet_runtime` | ROS-координатор, action-клиенты, раунды, обслуживание |
| `ros2_ws/src/capstone_nav2/launch/fleet_robot.launch.py` | Отдельные AMCL, RPP, costmap и safety каждого робота |
| `simulation/fleet` | Мир, карта и локальная физическая модель двух роботов |
| `ros2_ws/src/capstone_webots_bridge` | Энкодеры, LiDAR, моторы, общий clock, физические измерения |
| `scripts/run_fleet_system.py` | Подъём стека, запуск испытания, сбор результата и остановка |
| `scripts/evaluate_fleet.py`, `fleet_evidence.py` | Независимый аудит физики, назначений и журналов |

У каждого робота свой namespace: `/robot_1` или `/robot_2`. TF передаётся через
отдельные топики; имена кадров внутри каждого стека остаются `map`, `odom`,
`base_link`. Карты описывают одну мировую систему координат. `/clock` общий,
публикует его только первый bridge. Многороботный прогон начинает новый процесс
Webots, индивидуальный reset отключён.

## Доказательства в каталоге результата

- `runtime/events.csv`: выпуск заявок, назначение, обслуживание, начало и конец раундов.
- `runtime/assignment_N.yaml`: матрица стоимости и выбранное сопоставление.
- `runtime/plans.csv`: независимые и совместные пути каждого робота.
- `runtime/plans/plan_N.yaml`: конфликты, стоимость, нижняя оценка и раскрытия поиска.
- `physical/trajectory.csv`, `contacts.csv`: исходные физические измерения.
- `physical/audit.yaml`: проверка каждой доставки, расстояний, контактов и остановки.
- `provenance.json`, `logs/`: параметры, версии, хеши исходников и логи процессов.

Аудитор независимо проверяет отсутствие повторных назначений, соответствие
сопоставления матрице стоимости, порядок обслуживания и фактическую позицию
робота у нужной станции. Для маршрутов проверяет исходные конфликты, отсутствие
оставшихся конфликтов, проходимость статической карты и физическое исполнение
каждого раунда. Успешный статус координатора сам по себе не даёт `PASS`.

В библиотечных тестах CBS сопоставляется с независимым совместным Dijkstra
на всех 900 упорядоченных конфигурациях двух роботов на сетке 3×2. ECBS проверяется
на тех же конфигурациях с `w=1.1`, `1.5`, `2.0`. Назначение дополнительно сравнивается
с полным перебором матриц. Это дополняет физический прогон, а не заменяет его.

## Подтверждённые физические результаты

Оба метода прошли `queued.yaml` с двумя роботами и четырьмя заявками.
В каждом прогоне проверены 16 совместных раундов, два назначения, загрузка
и доставка всех грузов, физические контакты и конечная остановка.
Пути каждой встречной доставки содержали два исходных конфликта; в совместных
планах осталось ноль. Истинная поза использована только для независимого аудита.

| Метод | Доставки | Контакты | Минимальная дистанция, м | Максимальное отклонение, м | Время миссии, с |
|---|---:|---:|---:|---:|---:|
| [CBS](../experiments/fleet/cbs-queued/physical/audit.yaml) | 4/4 | 0 | 0.961 | 0.0971 | 121.24 |
| [ECBS, w=1.5](../experiments/fleet/ecbs-queued/physical/audit.yaml) | 4/4 | 0 | 0.944 | 0.0968 | 121.20 |

Дистанция измерена между центрами корпусов радиуса 0,28 м. Допуск аудитора
на отклонение от ребра — 0,12 м; максимальный интервал физических измерений
в обоих прогонах — 0,02 с. Время симуляционное, от старта миссии до завершения
последней разгрузки. Разница двух отдельных измерений не доказывает превосходства
одного метода по времени физических доставок.

Стоимость каждого встречного плана — 14 шагов у обоих методов. CBS вернул
нижнюю оценку 14 и раскрыл четыре узла дерева ограничений. ECBS вернул нижнюю
оценку 13 при `w=1.5`, раскрыл два узла и действительно использовал FOCAL за
пределами минимального `f`. Проверка границы относится к дискретной стоимости.

Вторые заявки поступили на пятой секунде и дождались завершения первого рейса.
Матрица стоимости первого назначения — `[[0,6],[6,0]]`, второго —
`[[6,0],[0,6]]`; в обоих случаях выбрано сопоставление суммарной стоимости 0.
Таким образом, вторую пару получили роботы, уже оказавшиеся у соответствующих
станций загрузки. Повторного владения одной заявкой и двух грузов у одного
робота аудитор не обнаружил.

[Протокол, графики, исходные измерения и контрольные суммы](../experiments/fleet/README.md)
сохранены в репозитории. Регрессионные проверки: `colcon test-result` сообщает
180 тестов без ошибок, Python-аудитор — 37 тестов без ошибок; изменённые
Python-файлы прошли `ament_flake8`.

Отдельно прошла [отмена во время движения](../experiments/fleet/cancel/physical/audit.yaml):
роботы проехали 1,527 и 1,487 м, первый совместный раунд завершён, второй
прерван. Контактов нет, остановка обоих роботов подтверждена координатором
и независимым физическим аудитором. Воспроизведение:

```bash
make fleet-test FLEET_METHOD=ecbs FLEET_ARGS='--mode cancel'
```

## Границы реализации

Исходная одиночная система G5 с EDD/DQN сохранена:
[её команды и устройство](G5_WEBOTS_NAV2.md). Многороботное назначение использует
явный алгоритм минимальной стоимости; существующая одиночная DQN не выдаётся
за обученную политику управления флотом. Базовая навигация Nav2 остаётся
интеграционной реализацией, без заявления о выполнении исследовательских
методов CNN-карты стоимости и MPC/PPO из первоначальных заданий G3/G4.

Планировщик, диспетчер, action-клиенты и bridge реализованы на C++.
Внешний сценарный запуск и независимый аудитор этого интеграционного стенда —
Python-инструменты проверки; они не заменяют штатный C++ benchmark G5 и не
заявляются как многороботная реализация конкурсного benchmark из README.
